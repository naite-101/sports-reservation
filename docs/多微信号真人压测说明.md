# 多微信号真人并发压测说明

> 这是**唯一**能真实复现「200 人同时抢同一场地」的方案。
> 因为抢场地需要 200 个**真实不同 openid**，而 openid 是微信按登录用户身份自动注入的，
> 本地 mock 和 HTTP 外部压测都无法模拟——只有真人、真微信、真 openid 能测出真实并发表现。

---

## 一、为什么只有这条路是真的

项目鉴权代码（`application.js`）：

```js
const wxContext = dbUtil.getCloud().getWXContext();
openId = wxContext.OPENID || '';
```

`openid` 是微信平台注入的**唯一可信身份**：

| 方式 | openid | 能否测「抢场地」 |
|---|---|---|
| 本地 mock | 手动造假的 openid | ❌ 假的，碰不到真实云数据库并发隔离 |
| HTTP 外部压测 | 空 | ❌ 所有人变匿名，被 4003 拦截 |
| **真人真微信点按钮** | **真实、各不相同** | ✅ **唯一真实路径** |

---

## 二、已新增的压测页

`miniprogram/pages/stress/stress`（已注册到 `app.json`，**未加入底部 tabBar**，普通学生看不到）。

功能：
- 显示当前登录者身份（姓名、是否已完善信息）
- 显示目标日期 / 场次 / **目标场地**（所有人抢同一个）
- 一个大「抢！」按钮：点击记录本地毫秒时刻 → 调真实 `reservation/create`
- 显示结果：成功 / 失败（含具体 code：4100 场地已满、4101 重复、4010 未完善信息等）
- 「释放」按钮：取消自己抢到的场地，便于重复测试

---

## 三、怎么组织一次真人压测

1. **重新上传代码**：云函数重新上传部署 + 小程序重新上传体验版（因为改了 `index.js`、`app.json` 和新增页面）。
2. 让 N 个同学（每人一个微信号）都打开体验版，先各自**完善个人信息**（否则会被 4010 拒绝）。
3. 进入压测页：开发者工具里编译到 `pages/stress/stress`，或体验版里加一个临时入口跳转。
4. 大家在页面里确认看到的是**同一个目标场地**（比如都是 `badminton#1`）。
5. 约定一个时间，比如「我喊 3、2、1，大家同时点『抢』」。
6. 观察结果：**只有 1 人显示「抢到了」，其余人都显示「场地已被别人抢走」(4100)**。
7. 用「释放」按钮清空场地，可再测下一轮。

## 四、期望结果与判定

| 现象 | 含义 |
|---|---|
| 恰好 1 人成功，其余 4100 | ✅ 并发正确，`_id` 组合主键 + 唯一索引兜底生效，系统稳定 |
| 超过 1 人成功 | ❌ 超约 bug，需排查（几乎不可能，`_id` 主键天然唯一） |
| 有人报 4101 | 正常（同一人同时间窗约了别的场地），不代表错误 |
| 有人报 4010 | 该同学没完善信息，让他去完善 |
| 大量 5xx / 网络异常 | ⚠ 云端扛不住并发，看云开发控制台日志 |

---

## 五、局限（如实）

1. 需要真人配合，N 越大越难组织；几十人已能充分验证「抢同一场地只 1 人成功」的并发正确性。
2. 真人点按钮的「同时」精度受网络、手速影响，不像脚本那样精确到毫秒，但**已经足以验证核心并发约束**。
3. 若要测「云函数在高并发下会不会崩/限流」，请配合「外部 HTTP 并发压测」（见另一份文档），两者互补。
