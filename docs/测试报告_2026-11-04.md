## 二、发现的问题及处理

### 问题 1：5 个测试用例过期（非业务 bug）

**现象**：首次运行 5 个用例失败，全部集中在"人事权限/角色"模块。

**根因**：之前做了「角色合并」（老师/主席 → 人事管理员 HR_ADMIN=4），`config.js` 删除了 `TEACHER`/`CHAIRMAN` 常量，但测试用例仍引用旧常量，导致 `config.ROLE.TEACHER` 为 `undefined`。

**处理**：已更新测试用例对齐新角色模型，重跑后全部通过。**业务代码本身无 bug**。

涉及文件：
- `test/03_config_codes.test.js`（角色常量断言）
- `test/08_behavior.test.js`（4 个人事权限用例）

## 四、核心结论：1000 人同时抢会不会崩？

### ✅ 代码逻辑层（已充分验证，不会崩）

- 1000 并发抢同一场地：**只有 1 人成功，999 人被正确拒绝，0 异常、0 个 500**。
- 多轮测试（200/500/1000×3）结果完全一致，可重复性极好。
- 核心保证：`日期_场次_场地` 作为 `_id` 组合主键（天然唯一）+ 唯一索引 `uniq_student_slot` + 事务内 doc 预检，从设计上杜绝「超约」和「重复预约」。

### ⚠️ 真实云端承载层（本地无法验证，需注意）

本地 mock 测不出微信云端的**真实调度 / 限流 / 实例扩容 / 数据库连接池**。真实 1000 并发是否会"限流/变慢"取决于：

1. 云函数并发实例数配额（免费/低配环境可能有上限）；
2. 云数据库连接数上限；
3. 环境流量配额（超出可能返回 429 限流，但这是"限流保护"，不是"崩溃"）。

云函数超时已设为 60 秒，单次预约远小于此值，正常不会超时。

### 要测真实云端，还需一步

HTTP 网关当前返回 `INVALID_PATH`，说明 **`/gym` 路由还没在控制台配置**。配置后即可跑真实并发压测：

1. 云开发控制台 → HTTP 访问服务 → 路由管理 → 新建路由，路径 `/gym`，关联 `cloud` 云函数；
2. 运行 `node test/stress_http_concurrent.js 1000 1000`（注意：只能打只读路由，测云函数承载能力，测不了"抢场地"——那需要真实 openid）。

1. **HTTP 网关路由未配置**：`/gym` 路由需在云开发控制台手动创建，之后才能做真实云端并发压测。
