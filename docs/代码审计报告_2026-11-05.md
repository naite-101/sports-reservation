## 1. 审计概览

**整体风险：中高危。** 核心并发防超约设计（`reservations` 组合主键 `_id=日期_场次_场地` + 云数据库事务 + `student_slot_locks` 学生时段锁）扎实可靠，21:00 高峰 200 人并发抢约**未发现可超约的路径**；身份鉴权基于微信 `getWXContext().OPENID`（客户端不可伪造），无自定义 token 泄露面；错误处理统一返回不泄露堆栈。这些是做得好的部分。

但对照需求规格的角色与权限约束，**权限模型存在系统性越权缺陷**：后端采用「线性角色等级 `role < routeDef.role`」做鉴权，而需求要求的是**双向隔离**（人事不能解除黑名单、超管不能做人事任免），线性等级在数学上无法表达这种双向限制，直接导致 3 类越权（高危 H1–H3）。此外生产包内置了自动解题验证码的抢约页面（H4）、部署密钥硬编码且存在免登录 HTTP 触发面（H5）。业务规则层面，「拉黑固定 10 天」「普通管理员可设置临时闭馆」「未完善信息仅浏览公告」等条款与实现不符（见 §5）。

| 维度 | 结论 | 说明 |
|---|---|---|
| 业务逻辑（21 条规则逐条核对） | ⚠️ 部分不符 | 详见 §5 清单；核心预约/签到/二维码链路实现正确 |
| 权限&越权 | ❌ 严重缺陷 | 超管↔人事权限互穿、线性等级模型缺陷（H1–H3） |
| 数据库&并发安全 | ✅ 基本可靠 | 组合主键+事务防超约成立；存在闭馆竞态（M4）等小窗口 |
| SQL/NoSQL 注入 | ✅ 未发现 | 云开发 command 构造查询 + 控制器层类型校验，无字符串拼接 SQL |
| 接口安全 | ⚠️ 有隐患 | 密钥硬编码+HTTP 入口（H5）、定时任务可伪造（M2）、签到不绑 token（M1） |
| 小程序前端专项 | ⚠️ 有隐患 | storage 未存敏感数据（好）；但内置抢约脚本（H4）；路由/按钮隐藏不构成防护（后端已另行核验） |
| 代码质量/可维护性 | ⚠️ 一般 | 魔法数字、README 与代码不同步、注释尚可、异常处理较完整 |

**问题统计**：高危 5 项、中危 9 项、低危 10 项、需求不符 10 项。

### H-1 人事管理员可解除黑名单、可行使超管全部职权（线性角色等级导致越权）

### H-2 超级管理员可执行人事任免（违反「超管不能执行人事任免权限」）

| 项 | 内容 |
|---|---|
| 问题描述 | `hr/admin_list`、`hr/admin_add`、`hr/admin_assign`、`hr/student_*` 路由声明 `role: 3`，超管（3）全部可调用；`hr_service.assignableRoles` 明确允许超管任命普通管理员。超管实际拥有完整人事任免入口 |
| 风险等级 | **高危** |
| 对应需求条款 | 角色清单 3：「超级管理员……**不能执行人事任免权限**」；角色清单 4：「**仅**老师、现任主席这两个角色拥有人事权限」（`docs/PRD.md` 3.3 同样写明「人事权限仅老师/主席」） |
| 危害 | 超管可任免/调整普通管理员、可查看和修改学生个人信息（`hr/student_edit`），人事权限边界被打破；与 H-3 叠加后超管可直接废掉人事管理员 |
| 代码定位 | `cloudfunctions/cloud/config/route.js:63-69`（hr/* 均为 role:3/4）；`cloudfunctions/cloud/project/service/hr_service.js:35-44`（`assignableRoles` 给 SUPER_ADMIN 返回 `[ADMIN]`）、`hr_service.js:55-98`（adminAdd） |

**修复代码**：


### H-3 管理层可互相降级/禁用（adminAssign/adminAdd 缺少对目标现有角色的保护）

| 项 | 内容 |
|---|---|
| 问题描述 | `adminAssign` 只校验「目标**新**角色是否可任命」，不校验「目标**现有**角色」；`adminAdd` 对已存在用户直接覆盖 `role`。因此：①超管可对人事管理员（role 4）调用 `adminAssign(role=2)` 把其降为普通管理员甚至 `status=0` 禁用；②人事可把超管降级；③`adminRemove` 的 `user.role >= operator.role` 拦不住「超管对人事」方向（因为该接口 route role:4 只有人事能调，但人事可降超管，见下） |
| 风险等级 | **高危** |
| 对应需求条款 | 角色清单 3「不能执行人事任免权限」、角色清单 4「负责**普通管理员**任免、管理员权限分配/禁用删除」——均暗示不得操作更高阶角色 |
| 危害 | 恶意/误操作可一键废掉超管或人事账号（越权破坏权限体系完整性）；人事可通过「任命自己信任的人为超管→让其解除黑名单」绕过 H-1 的限制 |
| 代码定位 | `cloudfunctions/cloud/project/service/hr_service.js:131-146`（adminAssign 无目标角色校验）、`hr_service.js:77-95`（adminAdd 覆盖已有用户 role）、`hr_service.js:118-128`（adminRemove 仅比对等级） |

**修复代码**：

```js
// ===== hr_service.js：adminAdd / adminAssign 统一加目标保护 =====
assertCanOperateTarget(operator, targetUser) {
  const opRole = Number(operator.role);
  const tgRole = Number(targetUser.role);
  // 1) 只允许操作「普通管理员」（需求：普通管理员任免）
  if (tgRole !== config.ROLE.ADMIN && tgRole !== config.ROLE.STUDENT) {
    this.AppError('仅可操作普通管理员或学生账号', appCode.NO_RIGHT);
  }
  // 2) 目标现有角色必须严格低于操作者
  if (tgRole >= opRole) {
    this.AppError('不能操作同级或更高权限的成员', appCode.NO_RIGHT);
  }
}

// adminAssign 修改前：
const user = await UserModel.getOne(openid);
if (!user) this.AppError('用户不存在', appCode.LOGIC);
this.assertCanOperateTarget(operator, user);

// adminAdd 对已存在用户修改前同样调用 assertCanOperateTarget；
// 且新角色仅允许 config.ROLE.ADMIN（配合 assignableRoles 只返回 [ADMIN]）
```

## 3. 中危隐患（业务异常、可被绕过，影响功能正确性）

### M-1 `admin/checkin` 不绑定二维码 token：可凭 res_id 直接签到

- **问题描述**：二维码安全链路只存在于 `admin/scan`（校验 token 有效期）；确认签到的 `admin/checkin` 只收 `res_id`，**不校验、不消费任何 token**。攻击者（或被入侵的管理员端）无需扫描，直接构造 `res_id` 即可为任意预约完成签到。
- **风险等级**：中危
- **对应需求条款**：需求 5②「必须服务端校验有效期……截图二维码无法签到」、5③「扫码校验预约场次、学生身份匹配」
- **危害**：「签到必须经有效动态二维码」的服务端强制点缺失，伪造签到/替签可行；截图防作弊只防了 scan 半程。
- **代码定位**：`cloudfunctions/cloud/project/service/checkin_service.js:41-131`（checkin 无 token 参数）；`cloudfunctions/cloud/project/controller/admin_controller.js:22-30`
- **修复代码**：

```js
// checkin_service.js —— checkin 必须携带并校验 20 秒内有效的 token
async checkin(operator, { token, res_id, slot_key, companions }) {
  const tokenDoc = await QrcodeTokenModel.getOne({ token: String(token || '') });
  if (!tokenDoc || !tokenDoc.expire_time || tokenDoc.expire_time <= timeUtil.now()) {
    this.AppError('二维码已过期，请刷新后重试', appCode.QR_EXPIRED);

  const res = await ReservationModel.getOne(res_id);

  if (res.student_openid !== tokenDoc.student_openid) {
    this.AppError('二维码与预约身份不匹配', appCode.SLOT_MISMATCH);
  }
  // ...原有 slot_key / 闭馆 / 幂等 / 签到窗口校验不变
}
```


### M-2 定时任务可被任意调用方伪造触发，job_secret 形同虚设

- **问题描述**：`application.js` 入口第一行判断 `event.Type === 'Timer' || event.triggerType === 'timer' || event.TriggerName` 即进入 `runTimerJob`，**不校验 job_secret**。而 event 完全由调用方构造，任何学生用 `callFunction` 传 `{TriggerName:'gymreserve-expire'}` 即可直接执行 job/expire、job/notify。

6. **个人信息字段与需求不符：缺「班级」。** 需求 7 要求「姓名、班级、学号、电话」；实现字段为 name/student_no/phone/**college（学院）**，无班级。→ `users` 表、`passport/save_profile`、`profile` 页、`hr/studentEdit` 补 `class_name` 字段。
