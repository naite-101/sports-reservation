# 云端冒烟测试说明（真实环境验证）

> 目标：**不是**本地 mock，而是在**已部署的微信云端**真实验证项目是否稳定、部署是否完整。
> 本地 mock 只能证明「代码逻辑写对」，验证不了「云端环境是否真实可用」——本冒烟测试补上这一环。

---

## 一、为什么需要这个测试

项目现有 49 条回归测试全部跑在本地内存 mock（`test/_mock_cloud.js`）里，用一个假数据库、假事务。它证明的是**代码逻辑正确**，但以下「只有云端才会暴露」的问题它测不出来：

| 现实才有的问题 | 本冒烟测试能否暴露 |
|---|---|
| 11 个集合是否真的都建好了 | ✅ 第 1 项 |
| 场馆/场次/配置是否初始化到位 | ✅ 第 2 项 |
| `reservations._id` 组合主键在**真实云数据库**能否防超约 | ✅ 第 3 项 |
| `uniq_student_slot` 唯一索引是否**手动建好**（README 第 5 步） | ✅ 第 4 项（最关键） |
| 预约→释放→再约 完整事务链路在云端是否正常 | ✅ 第 5 项 |

---

## 二、怎么运行（云端真实调用）

冒烟测试写成了云函数的一个**受密钥保护的路由** `smoke/run`，和 `init/run` 一样，只在你手动传正确 `job_secret` 时才会执行。

**前提**：先把改动后的云函数重新部署到云端（上传并部署 `cloudfunctions/cloud`）。

然后在**微信开发者工具**里：

1. 左侧资源管理器 → 云开发 → 云函数 → 找到 `cloud` 函数
2. 右键 → 「云端测试」
3. 输入测试参数（JSON）：

```json
{
  "route": "smoke/run",
  "job_secret": "gymreserve-job-secret-2026"
}
```

4. 点击「运行」，观察返回结果

> 密钥 `gymreserve-job-secret-2026` 在 `cloudfunctions/cloud/config/config.js` 的 `JOB_SECRET` 字段，若你改过就用你改后的值。

## 三、结果怎么看

返回结构：

```json
{
  "code": 200,
  "data": {
    "passed": 5,
    "total": 5,
    "all_ok": true,
    "results": [
      { "name": "集合齐全(11个)", "ok": true, "detail": "全部存在" },
      { "name": "初始化数据(场馆/场次/配置)", "ok": true, "detail": "场馆=32 场次=6 ..." },
      { "name": "组合主键防超约(同一_id并发只1成功)", "ok": true, "detail": "3次并发插入同一_id，成功=1 被拒=2" },
      { "name": "uniq_student_slot 唯一索引", "ok": true, "detail": "第二次约不同场地被拒 → 索引已生效" },
      { "name": "预约→释放→再约 完整链路", "ok": true, "detail": "预约→取消→再约 成功" }
    ]
  }
}
```

### 每一项的含义与异常处理

| 项 | `ok: true` 含义 | `ok: false` 时怎么办 |
|---|---|---|
| 集合齐全(11个) | 11 个集合都在 | 重新运行 `init/run` 建集合 |
| 初始化数据 | 场馆/场次/配置都写入 | 重新运行 `init/run` |
| 组合主键防超约 | 云数据库 `_id` 主键真实唯一，3 个并发插同一 `_id` 只 1 成功 | 几乎不可能 false，若 false 说明云环境异常 |
| **uniq_student_slot 唯一索引** | 同一学生同时间窗约第二个场地被数据库拒绝 | **去云开发控制台手动建索引**（README 第 5 步，字段 `student_openid+date+slot_key`，唯一） |
| 预约→释放→再约 | 完整业务链路在云端跑通 | 看 `detail` 里的错误码定位 |

> **第 4 项（唯一索引）是最需要关注的**：如果它 `ok: false`，说明「同一学生同一时间窗跨场馆约多个」目前只靠应用层「先查后插」兜底，**高并发下有竞态风险**，这是本地 mock 完全测不出的真实隐患。

---

## 四、测试数据是否污染线上？

不会。冒烟脚本所有写入都用了 `SMOKE_` 前缀的临时主键 / 临时 openid，**每一项执行完立即在 `finally` 里清理**，不会残留真实学生的预约数据。

---

## 五、局限（如实说明）

1. 本冒烟测试验证的是**部署完整性和关键约束是否生效**，是「真不真」的问题，不是「扛不扛并发」的问题。
2. 「200 人同时抢同一场地会不会崩」需要**真实并发压测**（见 HTTP 触发器压测方案），本测试的第 3 项只做 3 个并发插入，用于确认主键唯一性，不代表 200 并发表现。
