# 外部真实并发压测说明（HTTP 访问服务）

> 目标：从**本机**向**已部署到微信云端**的云函数发真实并发 HTTP 请求，
> 测出云函数在真实并发下的稳定性：成功率 / 延迟 / 限流 / 超时 / 5xx。
> 这比本地 mock 真实得多——本地 mock 完全碰不到微信云端的真实调度、限流、实例扩容。

---

## 一、原理与边界（先说清楚）

微信云开发的云函数有两种被调用方式，身份来源完全不同：

| 调用方式 | openid 来源 | 能否测"抢场地" |
|---|---|---|
| 小程序内 `wx.cloud.callFunction` | 微信按登录用户自动注入，**真实** | ✅ 能（但要 200 个真人） |
| HTTP 访问服务（外部 curl/脚本） | **无**，`getWXContext().OPENID` 为空 | ❌ 不能（所有人都是匿名，被 4003 拦截） |

所以：

- **本压测脚本测的是「云函数本身扛不扛得住并发」**，打的是不需要 openid 的只读路由（`notice/latest`、`config/get`）。
- **「200 人同时抢同一个场地」无法用 HTTP 外部模拟**（缺真实 openid），那是另一个方案（多微信号真人压测，见另一份文档）。

---

## 二、改动清单（本次已改好，需重新部署）

1. **`cloudfunctions/cloud/index.js`**：新增 HTTP 触发分支——检测到 `event.httpMethod` 时，把 HTTP 请求体里的 `{ route, ... }` 交给原有 `application.app` 统一处理，再包装成 `{ statusCode, body }` 返回。**不影响**小程序 `callFunction` 和定时触发器。
2. **`test/stress_http_concurrent.js`**：新增的外部并发压测脚本（Node 22 原生 `fetch`，无第三方依赖）。

## 三、部署 + 开启 HTTP 访问（一次性）

1. **重新上传云函数**：在微信开发者工具 → 云开发 → 云函数 `cloud` 右键 →「上传并部署：云端安装依赖」。
2. **开启 HTTP 访问**（关键，代码改不了，必须控制台手动开）：
   - 云开发控制台 → HTTP 访问服务（或「HTTP 网关」）→ 路由管理 → 新建路由
   - 触发路径：`/gym`（自定义）
   - 关联资源类型：云函数 → 选 `cloud`
   - 保存后得到一个公网 URL，形如：
     `https://<你的环境ID>.service.tcloudbase.com/gym`

> 实际 URL 以控制台生成的为准，可能带不同地域前缀。

## 四、运行压测

```bash

# 自定义并发数和总请求数
node test/stress_http_concurrent.js 500 1000

# 通过环境变量指定 URL（如果你的 URL 不是默认格式）
```

## 五、结果怎么看

脚本会输出：

- **成功率**：正常应接近 100%。
- **吞吐（请求/秒）**、**延迟分布（最小/中位/95%/最大）**。
- **状态分布**：`200` 成功、`429` 限流、`超时`、`5xx` 等。

### 判定

| 现象 | 含义 | 应对 |
|---|---|---|
| 全部 200 | 云函数在 N 并发下稳定，未崩未限流 | 可逐步加大并发再测 |
| 出现 429 | 被云开发网关限流 | 并发过大，或需要提升环境配额 |
| 出现超时 | 云函数处理不过来（默认超时 60s） | 检查是否有慢查询、提升函数超时或优化 |
| 出现 5xx | 云函数内部报错/崩溃 | 看云开发控制台的函数日志定位 |

## 六、局限性（如实）

1. 只压**只读路由**，不压「抢场地」的写事务——那需要真实 openid。
2. HTTP 触发多了一层网关，延迟会比小程序 `callFunction` 略高，但**并发稳定性结论是真实可信的**（因为跑在真实云端、真实调度上）。
3. 免费环境可能有并发/流量配额，压测结果里若出现大量 429，不一定是代码问题，可能是环境配额限制，需结合控制台监控判断。
