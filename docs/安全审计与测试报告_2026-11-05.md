## 🔴 高危漏洞（破坏业务、越权、并发问题）

### H1. 超级管理员越权访问人事接口（垂直越权）

- **问题描述**：人事接口（管理员任免、权限分配、维护学生信息）的 `role` 门槛被设为 `3`（超级管理员），而非 `4`（人事管理员）。超管本应「禁止人事管理员任免权限」，却可以调用人事接口。
- **对应需求条款**：硬性约束第 3 条「超级管理员【禁止人事管理员任免权限】」；第 4 条「人事角色（老师、现任主席）**仅有这两个角色拥有人事权限**」；PRD P0-18。
- **风险等级**：🔴 高危
- **危害**：超管可任免普通管理员、给他人分配/禁用管理员权限、查看并修改学生信息（含手机号等敏感个人信息），破坏「人事权限仅老师/主席」的角色隔离；且超管账号被攻破后权限被放大。
- **代码定位**：
  - `cloudfunctions/cloud/config/route.js` 第 63~69 行：`hr/admin_list`、`hr/admin_add`、`hr/admin_assign`、`hr/student_list`、`hr/student_detail`、`hr/student_edit` 均 `role: 3`（仅 `hr/admin_remove` 为 `role: 4`）。
  - `cloudfunctions/cloud/project/service/hr_service.js` 第 35~44 行 `assignableRoles()`：超管返回 `[ADMIN]`（允许任命普通管理员）；第 176~200 行 `studentEdit()`：超管可修改学生/普通管理员信息。
- **可直接使用的修复代码**（`route.js`，将人事接口全部收紧到 `role: 4`）：

```js
// ---------- 人事（仅人事管理员 role=4；超管禁止任免/权限分配/维护学生信息） ----------
'hr/admin_list':    { controller: 'hr_controller', action: 'adminList',    role: 4 },
'hr/admin_add':     { controller: 'hr_controller', action: 'adminAdd',     role: 4 },
'hr/admin_remove':  { controller: 'hr_controller', action: 'adminRemove',  role: 4 },
'hr/admin_assign':  { controller: 'hr_controller', action: 'adminAssign',  role: 4 },
'hr/student_list':  { controller: 'hr_controller', action: 'studentList',  role: 4 },
'hr/student_detail':{ controller: 'hr_controller', action: 'studentDetail', role: 4 },
'hr/student_edit':  { controller: 'hr_controller', action: 'studentEdit',  role: 4 },
```

> 同步清理 `hr_service.js` 中「超管可任命普通管理员」「超管可改学生信息」的分支（`assignableRoles` 的 `SUPER_ADMIN` 分支、`studentEdit` 中允许超管的分支），否则即使路由收紧，代码里仍残留超管逻辑。由于 `role:4` 已从路由层拦截超管，残留分支实际不可达，但建议一并删除以消除歧义。

### H2. 人事管理员可「拉黑学生」「解除黑名单」（权限模型缺陷导致越权）

- **问题描述**：系统采用「单一 role 数值，越大权限越高」的线性权限模型。人事管理员 `role=4` 数值最高，自动 ≥ `blacklist/add` 的 `role=2` 和 `blacklist/release` 的 `role=3`，从而获得「拉黑学生」「解除黑名单」权限。但需求明确禁止人事角色执行这两类操作。
- **对应需求条款**：硬性约束第 4 条「人事角色【禁止拉黑、禁止解除黑名单】」。
- **风险等级**：🔴 高危
- **危害**：人事管理员（老师/主席）可拉黑任意学生、解除任意学生的黑名单，绕过「拉黑/解除需普通管理员/超管执行」的职责分工，造成权力越位与审计混乱。
- **代码定位**：
  - `cloudfunctions/cloud/config/route.js` 第 53~55 行：`blacklist/add: role 2`、`blacklist/release: role 3`。
  - `cloudfunctions/cloud/framework/core/application.js` 第 86 行 `if (role < routeDef.role)`：只做「下界」判断，未排除「人事角色」。
- **可直接使用的修复代码**（在 `blacklist_service.js` 两个方法入口处显式拒绝人事角色）：

```js
// blacklist_service.js 顶部已引入 config / appCode
const config = require('../../config/config.js');
const appCode = require('../../framework/core/app_code.js');

// add() 方法第一行追加：
async add(operator, { ... }) {
  if (Number(operator.role) === config.ROLE.HR_ADMIN) {
    this.AppError('人事管理员无拉黑权限', appCode.NO_RIGHT);
  }
  // ...原逻辑
}

// release() 方法第一行追加：
async release(operator, { ... }) {
  if (Number(operator.role) === config.ROLE.HR_ADMIN) {
    this.AppError('人事管理员无解除黑名单权限', appCode.NO_RIGHT);
  }
  // ...原逻辑
}
```

> 根本性建议：权限模型从「单一数值」升级为「角色能力清单」（RBAC）。即每个角色声明一组允许的 route/action 白名单，鉴权时查白名单，而不是比较数值大小。这能彻底消除「人事等级最高却要禁止某些操作」这类交叉约束无法表达的问题。

## 🟡 中危隐患（功能异常、可被绕过）

### M1. `JOB_SECRET` 硬编码在源码且已推送公开仓库

- **问题描述**：`config.js` 第 10 行 `JOB_SECRET: 'gymreserve-job-secret-2026'` 明文硬编码，且代码已推送至公开 GitHub 仓库 `naite-101/sports-reservation`。
- **对应需求条款**：PRD §3.3 非功能需求「权限隔离」；通用安全基线。
- **风险等级**：🟡 中危
- **危害**：任何看到仓库的人都能获得 `init/run`、`job/expire`、`smoke/run` 的密钥，可重建/清空数据、手动触发爽约拉黑。实际利用需持有小程序云函数调用权限，故未到高危，但属不良实践。
- **代码定位**：`cloudfunctions/cloud/config/config.js` 第 10 行；调用点 `framework/core/application.js` 第 35、45、70 行。
- **修复建议**：改为从云函数环境变量读取（`process.env.JOB_SECRET`），并从仓库移除明文；或改用每次部署随机生成并写入环境变量。

### M2. 爽约拉黑依赖定时触发器（非实时，且触发器可能未在云端生效）

- **问题描述**：爽约（场次结束未签到→自动拉黑）由 `job/expire` 完成，`config.json` 配置为每小时整点触发（`0 0 * * * * *`）。若触发器未生效，则爽约永远不会被拉黑。
- **对应需求条款**：PRD P0-17「爽约自动拉黑」；硬性约束第 6 条①。
- **风险等级**：🟡 中危
- **危害**：场次结束后最多延迟 1 小时才拉黑；若触发器未部署成功，则永久不拉黑（此前已观察到该现象）。
- **代码定位**：`cloudfunctions/cloud/config.json` 第 8~13 行；`project/service/job_service.js` `expire()`。
- **修复建议**：① 部署文档明确「触发器仅在云函数首次创建时自动建立，重新上传不会重建，需在控制台确认/补建」；② 在 `passport/login` 或 `my/reservations` 查询时对「已结束仍 pending」的本人记录做轻量补偿翻转（当前 `my_controller.reservations` 已在前端展示层标 expired，但未落库，可复用同一判断补写 `expired` + 自动拉黑）。

### M3. 需求文档与「硬性约束」存在两处口径冲突（需确认）

- **问题描述**：
  1. 拉黑时长：硬性约束第 6 条①「普通管理员拉黑，**固定 10 天**」vs PRD §3.2 通道 B「管理员手动拉黑，时长由操作者**自定义**」。当前代码为「自定义时长」。
  2. 场地闭馆：硬性约束第 2 条「普通管理员…**场地临时闭馆**」vs PRD §2.2/P0-15「场地闭馆为**超级管理员**能力」。当前代码 `venue/close` 为 `role:3`（超管）。
- **风险等级**：🟡 中危（口径不一致会引发验收争议）
- **建议**：与需求方确认最终口径。若以 PRD 为准，则代码现状正确（拉黑可自定义、闭馆仅超管），无需改动；若以硬性约束为准，则需把 `venue/close` 降为 `role:2` 并锁定拉黑时长。

### 2.3 并发场景模拟测试

**场景1：200 用户并发抢同一场地同一场次**
- 场景描述：同一 `date+slot+venue`，200 个不同 openid 同时 `reservation/create`（带正确验证码）。
- 预期正确行为：仅 1 人成功，其余 199 人收到 4100「场地已被预约」，零超约、零 500。
- 基于代码分析：`reservations._id = date_slot_venue` 主键天然唯一，事务内 `add` 主键冲突只放行 1 条，其余回滚 → **不存在超约**。
- **实测**（`node test/stress_200_concurrent.js 1000`）：1000 并发 → 1 成功、999 被 4100 拒绝、0 异常 → **PASS ✅**。

**场景2：并发混合（大量预约 + 同时取消释放场地）**
- 场景描述：N 人抢 M 场地，同时有用户取消已占场地，再有人抢刚释放的场地。
- 预期正确行为：取消后场地立即释放，可被他人再次预约；不会出现「占用表已删但流水仍 pending」或「重复占用」。
- 基于代码分析：
  - 取消在事务内**同时删除 `reservations` 占用 + `student_slot_locks` 锁**，保证释放原子性；流水表更新在事务外，`where{status:'pending'}` 条件更新，失败由 `job/expire` 兜底 → **无脏数据**。
  - 取消时间窗（开始前30min）与签到窗口（开始前15min）不重叠，`cancel` 与 `checkin` 不会真正并发冲突。
  - 闭馆联动取消与签到存在极低概率竞态，但 `checkin` 有「闭馆不可签到」校验兜底 → 可接受。
- **实测**（`node test/stress_multi_venue.js 1000 6`）：1000 人抢 6 场地 → 各场地恰好 1 人成功、994 被拒、0 重复、0 异常 → **PASS ✅**。

**结论**：并发控制正确，无超约、无脏数据；防超约与防重复均由数据库 `_id` 主键唯一性在事务内原子保证，是可靠实现。
